# 1.3.2-polish9 — track-change responsiveness candidate

Uncommitted development work on dev c7545b2 (polish8). Stable release remains
1.3.1. Owner device acceptance and measured latency/battery impact are pending.

## What changes

Music keeps its existing layout/buttons. Full-size 364px sharp covers now have
an optional persistent cache entry; revisiting a cached track avoids that decode.
Existing cover/thumb/background cache entries remain usable. Same-album art
reuse remains unchanged; unchanged Disco pixels are no longer re-tinted/rebound
just because the song path changed. Palette, accent and idle changes still repaint.

The live worker converts cover/background/sharp pixels and Disco's tint into
an owned prepared result. LVGL receives copies into stable display buffers;
workers never modify displayed memory or invoke LVGL. Superseded results are
freed. Preparation scratch is about 1.45MiB per result, normally transient;
allocation failure falls back to the original synchronous apply path.

Finished art is published before best-effort cache writes. The same worker keeps
ownership of its file outputs until writes finish; a new request replaces its
target rather than creating a competing decoder. Cache fingerprints, validation,
atomic writes, 1GiB free-space reserve and SD ownership guards remain. A new
sharp entry uses approximately 518KiB of SD space per cached track. Online art
is not cached as a local song's own picture.

Background prewarm checks admission again after taking the decode lock, yields
to live jobs and observes a two-second transport grace period. Cancellation
discards stale output and prevents further attempts; an already running bounded
in-process decode must finish its current call. No concurrent decoder pipelines.

Play history uses a bounded 32-entry FIFO and a dedicated SQLite connection on
a condition-variable worker. Idle work sleeps. Database contention can wait up
to roughly the old four-second budget there, never in the history enqueue call.
History remains best-effort: overload, database failure or abrupt process exit
can lose a pending record. No player/queue transaction is reordered.

Song Info's background file/DB refresh is deferred until the page is visible;
entry immediately requests the current state, and active-page updates continue.
Pending artwork uses 30ms delivery checks, returning to 120ms when the worker
finishes. Screen-off pausing remains. No added animations, frame-rate increase
or permanent busy polling.

## Validation

- Real SQLite exclusive-lock test: enqueue stays under 50ms on host, three events
  are committed with correct per-track counts; worker sleeps when idle.
- Production cache/pixel helpers: hits, missing/truncated files, source-identity
  changes, denied SD read/write admission, row orientation and both tint formulas.
- Eight real LVGL theme/appearance/side scenarios: unchanged same-album pixels;
  twelve rapid cross-album skips finish with the last track's sharp cover.
- Eight controlled stale-failure transitions across Ring, Braun and Disco.
- 44 existing LVGL interaction/immersive regressions.
- ASan/UBSan-instrumented production UI/history/main objects: all eight rapid-skip
  scenarios pass. This is host memory validation, not device performance evidence.
- Decoder, queue and theme/punctuation checks; static MIPS32r2 FP64 NaN2008 build.

Optional diagnostics: launch environment `DISKOS_PERF=1` logs transport tap/
acceptance, track report, artwork preparation and apply cost. Acceptance is not
proof that an IPC command has already left the local queue. The environment is
off by default; do not hot-replace or separately launch mq_ui over SSH to enable it.
